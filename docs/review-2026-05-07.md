# Project Review

**Date:** 2026-05-07
**Scope:** Full
**Project:** jobclass (Labor Market Occupation Pipeline)
**Reviewer:** Claude Code

## Executive Summary

The jobclass codebase is well-maintained with strong conventions, good test coverage (840+ tests), and consistent architecture. The most significant finding is **missing query parameter validation in the trends API**, where defined validation constants (`_VALID_METRICS`) are never actually applied. Secondary concerns include documentation drift in CLAUDE.md (archived file paths, stale lesson count), a CI matrix targeting the unreleased Python 3.14, and several god files exceeding 500 lines. Recommended priority: fix the validation gap in trends.py, then update documentation, then address CI and structural concerns.

## Findings

### [HIGH] F-01: Trends API skips query parameter validation

**Category:** Security
**Evidence:**
- `src/jobclass/web/api/trends.py:22-29` defines `_VALID_METRICS` with 6 allowed values
- `src/jobclass/web/api/trends.py:47-49` accepts `metric`, `geo_type`, and `comparability_mode` as raw strings without checking them against any allowlist
- `src/jobclass/web/api/trends.py:78` passes these values directly into parameterized SQL
- Contrast with `src/jobclass/web/api/wages.py:28-31` which correctly validates `geo_type` against `_VALID_GEO_TYPES`
- Affects endpoints: `/api/trends/compare/occupations`, `/api/trends/compare/geography`, `/api/trends/movers`

**Impact:** While parameterized queries prevent SQL injection, unvalidated parameters allow arbitrary metric/geo_type strings through to the database, returning empty results without helpful error messages. This is a defense-in-depth gap — the validation constant exists but is dead code.
**Fix:** Add validation checks at the top of `compare_occupations()`, `compare_geography()`, and `ranked_movers()`:
```python
if metric not in _VALID_METRICS:
    raise HTTPException(status_code=400, detail=f"Invalid metric: {metric}")
```
Define and apply a `_VALID_GEO_TYPES` and `_VALID_COMPARABILITY_MODES` set similarly.

### [MEDIUM] F-02: SQL string formatting in ranked_movers

**Category:** Security
**Evidence:**
- `src/jobclass/web/api/trends.py:206` uses `movers_sql.format(direction="DESC")` and `:211` uses `.format(direction="ASC")`
- The `direction` value is hardcoded (not user-controlled), so this is not currently exploitable
- However, `.format()` on SQL strings violates secure coding practice and could become dangerous if refactored

**Impact:** Not exploitable today since `direction` is hardcoded to `"DESC"`/`"ASC"`. Risk is future maintenance — someone could make `direction` a parameter without realizing the injection surface.
**Fix:** Replace with two separate SQL strings (one for DESC, one for ASC) or use a CASE expression in the SQL. Avoid `.format()` on SQL entirely.

### [MEDIUM] F-05: CI workflow targets Python 3.14

**Category:** Operations
**Evidence:**
- `.github/workflows/ci.yml:16` — lint job uses `python-version: "3.14"`
- `.github/workflows/ci.yml:25` — test matrix includes `"3.14"`
- `.github/workflows/ci.yml:49` — deploy job uses `"3.14"`
- Python 3.14 is in pre-release (alpha) as of May 2026

**Impact:** CI depends on a pre-release Python version. If GitHub Actions runners don't have 3.14 available, or if a 3.14 alpha introduces breaking changes, CI will fail unpredictably. The deploy job also uses 3.14, meaning static site deployment could break.
**Fix:** Change to `"3.13"` (current stable) or explicitly note that 3.14 pre-release testing is intentional. At minimum, keep the deploy job on a stable Python version.

### [MEDIUM] F-06: .env.example is incomplete

**Category:** Operations
**Evidence:**
- `.env.example` documents only `JOBCLASS_DB_PATH`
- `src/jobclass/config/settings.py` also reads `JOBCLASS_RAW_ROOT`, `JOBCLASS_MANIFEST_PATH`, and `JOBCLASS_MIGRATIONS_DIR`

**Impact:** New developers won't discover configurable environment variables without reading the source code.
**Fix:** Add the missing variables to `.env.example` with commented defaults.

### [MEDIUM] F-07: God files exceed 500 lines

**Category:** Architecture
**Evidence:**
- `src/jobclass/web/static/js/pipeline.js` — 2,228 lines (canvas rendering engine + data + interaction)
- `src/jobclass/load/timeseries.py` — 861 lines (metric definitions + loading logic)
- `src/jobclass/orchestrate/pipelines.py` — 779 lines (all 9 pipeline definitions)
- `src/jobclass/load/cpi_domain.py` — 760 lines (5 domain table loaders)
- `src/jobclass/parse/cpi_domain.py` — 649 lines (6 parser functions)

**Impact:** Large files are harder to navigate, review, and test. `pipeline.js` at 2,228 lines is particularly large for a single JS module.
**Fix:** Consider splitting `pipelines.py` into per-pipeline modules. Extract `pipeline.js` graph data (already partially in `pipeline_graph_data.js`) and interaction logic into separate modules. `timeseries.py` could separate metric definitions from loading logic.
